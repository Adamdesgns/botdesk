# BotDoor PC navigation without editing — local build, 2026-09-29

Adam said the bot may close windows but must not erase anything. A bot with unrestricted clicks and typing can delete through ordinary app controls even when the Delete key and file APIs are blocked. This build therefore makes PC-wide access a navigation mode: capture, inspect, list, focus, move the pointer, scroll, move or close the focused ordinary window, and start any local Windows `.exe` by exact path. The path of an open app is returned by window inspection for restarting it. Adam explicitly rejected a fixed program list because he cannot know in advance which app will freeze. The launcher takes no arguments and does not use a shell. It rejects click, drag, type, clipboard access and keys in PC-wide mode. One-window mode retains its existing editing controls.

The JavaScript guard and Windows native helper both reject PC-wide editing. The new move and close tools require a fresh capture of the exact foreground window, including its process, title and geometry. The native helper rechecks the window, ordinary desktop, process privileges and sensitive controls immediately before acting. Owner and MCP text state the restriction. Saving access rules still stops access and cancels schedules; GO LIVE remains separate. The 1.6 source was subsequently released after Adam approved the matched relay/host upgrade; see `PC-NAVIGATION-RELEASE-2026-09-29.md` for the live state.

Closing an app may discard unsaved work or trigger an app-specific prompt. Browser navigation, focus, and scrolling are not a Windows read-only sandbox, and no software can guarantee every app has no side effects. The reliable claim is that BotDoor does not deliver PC-wide click, typing, drag, clipboard, or editing-key commands in this build. Do not describe it as deletion-proof.

Local verification: `npm run check` passed 151 tests, relay types and the 21-tool MCP smoke. Native fake-window probes rejected a nonexistent program and forged target handles. The actual native helper launched a disposable blank Windows Forms executable by its exact path, focused its window, requested close and observed that process exit; the test-owned files were removed. This real trial exposed and fixed inherited stdio handles that initially made the launcher wait for the child to exit. A previous Notepad trial could not retain the exact window because this Windows Notepad build hands its UI to another process, so Notepad close is not counted as verified. The local portable is `dist-safeview/BotDesk-0.1.0-portable.exe`, SHA-256 `6F3EA2FC1D69887D5564D7DEF40EA5FC55AC94DA6A6EA051E341EA6C6FF87496`; packaged controller, guard, executor, Windows bridge, protocol, error contract and native helper bytes match source. Actual relay/phone acceptance remains separate.

Still needed for end-to-end acceptance: a bounded real-device session proves PC-wide viewing, window management and rejected edits through the relay and installed host. The launcher can start an existing local `.exe`, including a program that has side effects just by starting; there is no honest guarantee that unrestricted program launch can never erase data. The current command cannot end a background process that has no ordinary window, and does not discover installed apps that are not already open. This build-phase test used no token, GO LIVE, schedule, or remote input.
